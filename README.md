# tcslog-tools

Command-line tools for inspecting [tcslog](https://github.com/vomlehn/tcslog)
segment files.

`tcslog-dump` walks a whole log — a directory of segment files sharing a
prefix and suffix — and prints the records it recovers, with the losses it
found. `tcslog-dumphdr` prints one segment file's header, reading the bytes
it is handed and never the file's name, so it also serves a file that has
been renamed or copied out of its log.

The library is used from Rust, C/C++, and Python 3, and all three write the
same stored format, so these tools read a log whichever of them wrote it.

Both tools only read. They take `tcslog` with its default `write` feature
turned off, so neither needs the `TIMER_RESOLUTION` the writing side
requires at build time. The library's last two breaking changes have both
been outside what these use: `WriteCallbacks` became a trait in 0.3.0,
where it had been a structure of function pointers, which breaks every
caller that writes; and `Record` gained a field in 0.4.0, which breaks a
caller that builds or exhaustively destructures one. Neither tool writes,
and neither names `Record` — both read through `LogRead::read` into a
buffer of their own.

The library version required is 0.4. That version, not this crate's, is what
decides which stored segment file formats a build understands: it reads a
file whose major format version matches the library's and whose minor
version is no greater.

## Integration with cFS and F´

Work is under way on using tcslog with NASA's core Flight System (cFS) and
JPL's F´ (F Prime), and on these tools decoding the records a log holds with
definitions generated by [tcs-xtce](https://github.com/vomlehn/tcs-xtce), so
that what a vehicle stored reaches the ground as telemetry. The plan is in
tcspecial's [`docs/third-party.rst`](https://github.com/vomlehn/tcspecial/blob/main/docs/third-party.rst).

> **Note:** integration with cFS and F´ is a work in progress. None of it is
> built yet, and the plan may change as it is.

## Installing

Both tools install in `/opt/tcs/bin`, under `/opt/tcs`, the tree the TCS
packages share (FHS 3.0's `/opt/<package>`), with this README, the
licences, the changelog and the HTML manual in
`/opt/tcs/share/doc/tcslog-tools`, and `tcslog-tools-links`, which links
them into `/usr/local/bin`, in `/opt/tcs/sbin`. The library is linked
in, as Rust links its dependencies, so neither needs `tcslog` installed
to run.

As a package, built from a checkout (see *Building from a checkout*
below for the layout it needs):

```sh
make deb        # build/packages/tcslog-tools_<version>-1_<arch>.deb
make rpm        # build/packages/tcslog-tools-<version>-1.<arch>.rpm
make packages   # both
make packages STRIP=0   # both, unstripped
sudo apt install ./build/packages/tcslog-tools_*.deb
```

Both are made from one install into `build/stage/tcslog-tools` (`make
stage`), so they hold the same files. That install strips both binaries
with `strip --strip-unneeded`, about a quarter off each; `STRIP=0` keeps
them as cargo built them, for a debugger. The `-1` is the package's
release, `DEB_REVISION` for the .deb, for a package rebuilt from the same
source. Building them needs `rst2html` (`python3-docutils`)
and `dpkg-shlibdeps` (`dpkg-dev`). `make rpm` needs `rpmbuild` (`sudo apt
install rpm` on Debian) and says so, without failing, where it is
missing. A package also installs `/etc/profile.d/tcslog-tools.sh`, which
adds `/opt/tcs/bin` to `PATH` unless it is there already.

The .deb also carries what Debian expects of every package, outside
`/opt/tcs` as the hook is: `/usr/share/doc/tcslog-tools/copyright`, in
Debian's machine-readable format, and `changelog.Debian.gz`, both made
as the package is built from `LICENSE-MIT` and the version, and
lintian's overrides in `/usr/share/lintian/overrides/tcslog-tools`. The
RPM says the same in its own `License` and `%changelog`. `make
lint-packages` checks the packages that `make packages` built with
lintian and rpmlint, and their shell scripts with shellcheck. It skips,
in a line, any of the three that is not installed, and fails on any
finding that is not overridden; each override says why it is intended,
in `packaging/deb/tcslog-tools/lintian-overrides` and
`packaging/rpm/rpmlint.toml`.

Login shells find `/opt/tcs/bin` through `/etc/profile.d/tcslog-tools.sh`, but
sudo, cron and other minimal environments do not read it, and do not
find the programs. To make them available everywhere, link them into
`/usr/local/bin`, which is on every one of those paths, sudo's
`secure_path` included:

```sh
sudo /opt/tcs/sbin/tcslog-tools-links            # link them
sudo /opt/tcs/sbin/tcslog-tools-links --remove   # undo it
```

`--dir` names another directory, such as `/opt/bin`. It links only this
package's programs, leaves anything already in the way alone and says
so, and is never run for you: removing the package removes its links,
but installing it makes none. After `make install`, `sudo make links` and
`sudo make unlinks` do the same, with `LINKDIR` naming the directory.

Or straight from a checkout:

```sh
sudo make install               # under /opt/tcs, nothing in /etc
sudo make install HOOKS=1       # with /etc/profile.d/tcslog-tools.sh
make install PREFIX=$HOME       # into $HOME/bin
```

`DESTDIR` stages the install, and `make uninstall` removes it again,
honouring the same variables. `make install` strips as the packages do,
and `STRIP=0` keeps it from doing so. `HOOKS=1` needs the default
`PREFIX`, since the file it installs names `/opt/tcs`.

Or with cargo, from the registry or from a checkout:

```sh
cargo install --locked tcslog-tools
cargo install --locked --path . --root /opt/tcs
```

`--locked` builds with the dependency versions this crate was tested with,
which support Rust 1.75. Without it, Cargo before 1.84 picks the newest
versions, some of which need a newer Rust. Cargo also leaves its own
record of what it installed, `.crates.toml` and `.crates2.json`, in the
root it is given, which is why `make install` does not use it.

## tcslog-dump

```sh
tcslog-dump <dir> <prefix> <suffix> [--verbose] [--text] [--rec-size <bytes>]
```

Without options it prints one line per record and nothing else, which is
what to pipe into something else. A payload prints as hexadecimal: two
lower-case digits a byte, one space between, which assumes nothing about
telemetry that is mostly not text.

- `-v`, `--verbose` — also print a block for every segment file the read
  passed through, a notice wherever telemetry was lost or a record did not
  fit, a marker at each session boundary, and totals at the end.
- `-t`, `--text` — display payloads as ASCII. A printable character prints as
  itself; everything else prints as an escape — `\n`, `\r`, `\t`, `\\`, or
  `\xNN` — so that no byte of telemetry can move the cursor, start an escape
  sequence that swallows what follows, or break one record across two lines.
  The escape also says which byte was there. Without the flag a payload
  prints as hexadecimal.
- `--rec-size <bytes>` — the largest payload read without truncation, at
  least 1; 64 KiB (65536) unless given. A record with a longer payload
  prints cut short and marked, and `--verbose` says how many bytes were
  captured. The data header is read separately and does not count.
- `-h`, `--help` — print the options to standard output and exit 0, so the
  help can be piped. `--version` does the same. A usage error puts both the
  complaint and the help on standard error and exits 2, leaving standard
  output carrying nothing but what was asked for.

## tcslog-dumphdr

```sh
tcslog-dumphdr <file>
tcslog-dumphdr < <file>
```

Prints the header on a single line. It reads the file named on the command
line, or standard input when none is named. It reads only the header, so the
standard input form works on a pipe whose writer is still running. A read
failure exits 1 and a usage error exits 2.

## Building from a checkout

The `tcslog` dependency is a path to a sibling checkout, and installing and
packaging use [tcs-helpers](https://github.com/vomlehn/tcs-helpers), the
packaging scripts and make rules the TCS projects share, from a sibling
checkout too, so clone all three side by side:

```sh
git clone https://github.com/vomlehn/tcslog.git
git clone https://github.com/vomlehn/tcs-helpers.git
git clone https://github.com/vomlehn/tcslog-tools.git
cd tcslog-tools && cargo build
```

`cargo publish` substitutes the registry version for the `tcslog` path, so
a release does not depend on the layout. tcs-helpers is used where it is
checked out, never installed; `TCS_HELPERS=<path>` names a checkout
elsewhere, and `make tcs-helpers` checks that it is there and new enough,
which installing and packaging do first.
